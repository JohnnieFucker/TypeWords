# WordsBattle 游戏化 UI 与交互重构设计需求

本文可独立发送给设计 AI，无需先阅读代码。目标是重新设计 WordsBattle 的整体界面、信息架构和交互，让用户进入一个能通过背单词陪伴仙宠成长的游戏世界。允许重做页面结构、导航、品牌视觉和交互方式，不局限于给现有页面换皮。

本文中的「现有」指当前代码已具备的能力；「设计要求」是本次重构目标；「新增提案」需要额外开发，不能在交付中假装已经实现。

## 1. 给设计 AI 的任务

你是一位擅长养成游戏、教育产品和 Web 交互的资深产品设计师。请根据以下真实功能，设计完整的游戏化 Web 产品。

先提出世界观、信息架构和核心循环，再交付关键页面、完整操作流程、状态与反馈、设计系统、美术资源清单以及分阶段落地方案。必须覆盖学习和养成之间的连接，不能只输出一张漂亮的游戏首页。

产品以桌面端键盘背词为核心，同时适配手机浏览、查看仙宠和轻量互动。默认界面使用简体中文，保留后续多语言扩展能力。不要照搬当前布局，也不要把产品做成普通管理后台。

## 2. 产品定位与重构目标

**名称：** WordsBattle。代码基于 TypeWords，但面向用户的品牌应统一，避免两个名字混用。

**一句话定位：** 用真实的单词学习，推动仙宠成长、收集与冒险的轻量养成游戏。

**目标用户假设：** 希望坚持学英语、主要在电脑上用键盘练习，同时喜欢宠物养成与收集的用户。用户年龄和美术偏好尚未经过调研，不应直接假设成低龄儿童产品。

重构需要实现：

- 用户进入后知道「今天做什么」「我的伙伴怎么样」「学习会带来什么」。
- 学习、奖励、养成、旅行、切磋成为同一世界中的连续体验。
- 仙宠拥有存在感，成为玩家愿意返回的原因。
- 练习过程始终清晰、高效，键盘操作不被游戏装饰打断。
- 主要操作少跳转、少弹窗，错误和等待状态有明确去向。

不以提升刷屏时长为目标；不要用宠物死亡、强制倒计时或学习失败惩罚制造焦虑。

## 3. 现有产品事实

### 3.1 单词学习

- 选择系统词典或自定义词典，设定每日新词数量和复习安排。
- 支持跟写、拼写、识别、自测、默写、听写、随机复习等练习能力；实际入口与流程由练习模式配置决定。
- 支持 FSRS 间隔复习，复习任务数量与到期单词、复习比例及设置有关。
- 有单词发音、音标、释义、例句等学习信息，支持音效和快捷键设置。
- 支持查看和管理词典内容、自定义词典、导入导出，以及单词标记、收藏等操作。
- 有未完成任务、学习进度、学习记录和练习结算。
- 本地学习不要求登录；网络异常不应导致本地学习结果丢失。

### 3.2 仙宠与成长

现有五种灵兽及其属性：

| 灵兽 | 五行 |
| --- | --- |
| 小灵狐 | 火 |
| 月灵兔 | 水 |
| 青芽鹿 | 木 |
| 云羽鹤 | 金 |
| 山灵龟 | 土 |

首次建立登录用户的宠物数据时随机获得一只伙伴，附带一份行囊和一张寻缘符。目前不是自由选择初始宠物。

每只伙伴独立保存修为、属性和照料状态；可从已拥有的伙伴中切换同行者。每 100 点修为提升一级，等级从 1 开始；达到 5 级，阶段从「初生」变为「化灵」。现有阶段字段不等于已经拥有两套完整进化美术。

照料数值包括饱食、洁净、心情。三者分别每 4、6、8 小时下降 1 点，最低保留 20，不会死亡或消失。支持投喂、清洁和每日问候。

### 3.3 学习奖励和道具

- 学习进度同步到服务器后，对新增的有效学习日期发放每日奖励：一件随机照料道具和 25 点修为，同一天不重复发放。
- 不是每答对一题就获得 25 点修为，也不是每完成一组都再次发放每日奖励。
- 连续学习每满 3 天额外获得一件照料道具。
- 普通、优良、珍稀照料道具的抽取概率分别为 70%、25%、5%。
- 每日问候获得一份行囊和一张寻缘符，并提升心情。
- 首次获得、每日问候是当前行囊和寻缘符的明确来源，不要自行画出答题掉落这些资源的机制。
- 普通道具有灵谷饭、清泉露；优良有蜜桃饭、清风梳；珍稀有仙果拼盘、云锦沐浴，分别恢复照料状态。
- 保留旧版攻击、防御、灵力道具的使用能力，但它们不再作为普通学习掉落。
- 支持补发最近 7 天的未领取学习奖励，日期以北京时间为准。

### 3.4 寻缘与收集

消耗一张寻缘符，随机遇见一种灵兽，当前收服概率为 85%。收服未拥有的灵兽会加入图鉴；成功收服重复灵兽时，该灵兽获得 15 点修为。相遇可能失败，不能每次都播放「收服成功」。

### 3.5 离线旅行

消耗一份行囊后，当前伙伴出发旅行，目的地由服务器随机决定，约 1 小时后归来，带回纪念品、旅途文字记录和 15 点修为。

旅行按服务器时间计算，关闭页面仍会继续；重新读取游戏状态时结算。旅行中不能切换伙伴、使用道具、寻缘或切磋。现有机制不提供自由选择目的地、提前召回、加速或手动重复领奖。

### 3.6 异步切磋

- 每天最多主动发起 5 次，双方无需同时在线。
- 从服务端提供的对手列表中选择对手，不是实时匹配房间，也不等于已建立好友关系。
- 金克木、木克土、土克水、水克火、火克金；克制方力量提高 20%。
- 结果由属性、照料状态及少量随机值决定；服务端一次返回胜负和双方力量值。
- 主动挑战获胜获得 20 点修为，落败获得 10 点修为。
- 当前没有回合指令、技能选择、血量变化时间线或逐招战报。
- 可以设计简短对决演出，但不能把虚构的逐回合过程当作真实战斗记录。

### 3.7 账号与保存

当前已实现的是「电脑展示二维码 → 手机微信授权 → 电脑建立会话」。但项目持有的公众号是未认证订阅号，当前网页授权登录无法按现有方案正式使用，登录方案需要另外确认。

本次设计应包含游客、已登录、登录不可用三种状态。可以提供登录页结构和可替换认证入口，但账号密码、短信、扫码回复验证码等均不是现成功能，不应默认承诺。

学习数据主要在浏览器中保存，已登录用户可同步部分学习进度；仙宠、道具和切磋数据在服务端 SQLite 中保存。

同步限制：删除单词和回退学习位置目前不向其他设备同步；自定义词典仅同步单词原文，不同步全部释义及例句。不要用「所有数据已完整云备份」等文案。

## 4. 希望形成的游戏体验

推荐主循环：

> 回到自己的据点 → 查看今日学习与伙伴状态 → 开始单词修炼 → 完成本地学习结算 → 同步成功后确认真实奖励 → 照料或收集伙伴 → 旅行或切磋 → 下次回来继续学习。

可以将学习目标呈现为「今日修炼」，将复习呈现为「巩固修炼」，但必须同时保留「新词」「复习」「词典」等明确标签，不能让用户靠猜理解功能。

建议优先探索「灵兽伙伴与轻幻想冒险」方向：有可停留的场景、伙伴动作和可点击目标。可以提出差异明显的美术方向进行比较，例如东方绘本、温暖手绘、精致像素；选定一个方向后统一执行，不要把三者混成一套。

当前森林绿和奶油白配色、书页新芽 Logo 均可重新设计，不构成必须保留的视觉限制。品牌应适合长时间学习，并在小尺寸图标中保持辨识度。

## 5. 信息架构与页面范围

允许重组为「据点、修炼、伙伴、探索、切磋、个人与设置」等结构，以下是功能范围，不是强制导航标签。

| 设计范围 | 当前入口 | 重构需要解决的问题 |
| --- | --- | --- |
| 欢迎与进入 | `/` | 说明核心玩法；游客可直接开始；登录不可用时能继续操作 |
| 游戏主界面 | 主要分散在 `/words` 与 `/pet` | 统一今日目标、同行伙伴、主要行动与回访反馈 |
| 词典选择与管理 | `/dict-list`、`/dict` | 选择学习内容；显示进度；编辑、导入、导出和切换前保护 |
| 学习任务准备 | `/words` 及练习配置 | 解释新词、复习、数量、模式和未完成任务 |
| 单词练习 | `/practice-words/:id` | 键盘输入为中心，清楚区分题型、提示、错误与阶段推进 |
| 单词测试 | `/words-test/:id` | 题目、选项、作答反馈、快捷键和测试结果 |
| 学习结算 | 当前练习内弹窗 | 统计、本地保存、同步和奖励确认形成连续闭环 |
| 伙伴与照料 | `/pet` 内模块 | 伙伴成为视觉中心，道具操作有目标和结果反馈 |
| 图鉴与寻缘 | `/pet` 内模块 | 区分未拥有、已拥有、同行；呈现成功、失败与重复相遇 |
| 旅行与纪念品 | `/pet` 内模块 | 出发、进行中、归来、重复收藏与功能限制 |
| 切磋与记录 | `/pet` 内模块 | 选择对手、克制说明、剩余次数、结果与记录 |
| 学习记录 | `/words` 内模块 | 学习趋势、日期明细、新词、复习、错词和时长 |
| 设置与帮助 | `/setting`、`/help` | 学习、音频、复习、主题、快捷键、备份、账号与帮助 |

表中的游戏模块目前并非各自独立路由；可设计成页面、抽屉或场景面板，但需要说明进入、返回和手机端对应方式。不要因代码里存在旧组件就默认文章练习等历史功能属于本次主线。

## 6. 必须设计完整的交互流程

### 6.1 首次进入

看懂产品 → 游客开始或登录 → 选择词典 → 设置合理的学习数量 → 第一组练习 → 结算 → 知道下一步。

登录可用时补充首次获得伙伴的揭晓流程；若新增自由选宠，必须标为需要修改业务规则的提案。新手引导应可跳过、可重新查看，不能遮挡输入或迫使用户阅读长教程。

### 6.2 每日回访

一眼看见今日任务、未完成练习、伙伴状态和旅行情况。主要按钮随状态显示「开始修炼」或「继续修炼」，不要同时堆满同等权重的行动。

每日问候、学习奖励和三日连续奖励必须区分触发条件与领取状态，不能制造当前后端不存在的手动领取接口。

### 6.3 学习过程

设计待输入、输入中、正确、错误、查看提示、重试、题型切换、暂停、继续和完成状态。明确焦点在哪里、哪些键有效、怎样回到输入。

输入区域和目标单词是主角。同行宠物可以在边缘陪伴或对阶段完成作短反馈，但不要逐键播放全屏攻击、移动单词位置或要求鼠标点宠物才能继续。

错误反馈应告诉用户怎样继续；音频不可用时仍能完成可替代的操作。显示新词与复习的真实任务关系，不能伪造无限关卡和地图解锁进度。

### 6.4 结算与奖励

区分以下状态：本地结算中、本地保存成功、远端同步中、同步成功且获得奖励、同步成功但当日奖励已发放、同步失败待重试、游客仅本地保存。

奖励只展示服务端已确认的结果。离线或同步失败时可表达「学习已保存，联网后同步」，不能提前表现为资源已经到账。连续完成第二组仍可看到学习成绩，但不能再次显示当日首份奖励到账。

结算后提供「再来一组」「回到据点」「照料伙伴」等清楚的选择，避免多个连续遮挡的弹窗。

### 6.5 伙伴操作

照料：选道具 → 看清目标、数量与效果 → 提交 → 反馈真实变化。无道具、数量为零、旅行中、请求失败都要有说明。

寻缘：确认消耗 → 请求 → 短演出 → 展示收服成功、重复修为或未收服结果。演出可跳过，刷新不能触发重复消耗。

旅行：确认消耗 → 出发 → 显示预计归来时间 → 归来后展示纪念品与修为。倒计时只是展示，结算以服务器为准。归来数据已结算时不要再画一个会重复发奖励的按钮。

切磋：选对手 → 显示属性、克制和剩余次数 → 提交 → 播放可跳过的短演出 → 显示真实胜负与修为。旅行中、对手变化、次数耗尽和无对手都要有状态。

## 7. 全局状态与操作保护

设计稿至少覆盖：

- 初次无词典、无学习记录、无道具、尚未收集伙伴、无纪念品、无可挑战对手。
- 游客访问游戏模块、会话过期、登录配置不可用。
- 首次加载、局部提交中、网络断开、请求失败、保存失败、同步冲突和重试。
- 任务进行中切换词典、修改任务数量、离开练习，说明保存情况和影响。
- 行囊或寻缘符不足、当日已问候、今日奖励已发放、切磋次数耗尽。
- 旅行进行中、旅行时间已到但状态刷新失败、归来结算完成。
- 导入格式错误、导出、历史备份恢复和清除本地数据的风险确认。

消耗资源的提交中阻止重复点击；失败后允许明确重试。按钮不可用时说明原因。破坏性操作保留确认，不把危险操作包装成普通游戏按钮。

## 8. 视觉与动效要求

需要明确：场景构图、界面层级、中文与英文排版、色板、五行识别、道具稀有度、按钮、面板、弹窗、资源栏、进度、提示和图标语言。

五行和稀有度不能只靠颜色区分，应结合图形、文字或纹样。英文单词与音标使用易读字体，不使用影响字形识别的装饰字体；数值变化不引起布局跳动。

动效优先用于伙伴待机、问候、照料反馈、获得道具、修为增长、升级、寻缘揭晓、旅行出发归来和切磋结果。每种动效需说明触发、时长范围、可否跳过以及减少动态效果模式下的替代反馈。

音频分学习发音、输入音效、游戏反馈与背景音乐，分别可控。背景音乐属于新增提案，不默认已经存在；不能自动干扰单词发音。

禁止仅靠大面积发光、玻璃卡片、悬浮数字和装饰进度条制造游戏感。真正的游戏感来自场景、角色、目标、行动和可理解的结果。

## 9. 多设备与可访问性

- 桌面参考 1440×900，笔记本参考 1280×720，手机参考 390×844。
- 桌面支持完整键盘练习；手机端需说明软键盘弹出时如何保持题目、输入与反馈可见。
- 手机优先展示今日目标、伙伴互动、旅行和记录；不能直接把桌面缩成不可点的小地图。
- 核心操作支持键盘和可见焦点；场景热点同时提供可理解的文字入口。
- 控制对比度、触摸目标、文本溢出和弹层焦点，错误反馈不只依赖颜色、声音或动画。
- 长页面与弹层在低高度窗口中仍能操作，适配系统减少动态效果设置。

## 10. 现有技术与实现边界

前端为 Nuxt 4、Vue 3、TypeScript、Pinia、UnoCSS、SCSS，带有 i18n、图标和自建基础组件。服务端为 Nuxt/Nitro API，使用 SQLite；浏览器侧有 IndexedDB 等持久化逻辑。

UI 可以全面重构，但应复用练习引擎、复习调度、持久化和服务端业务规则。不要为换界面重写账号、数据模型或学习算法，不要未经说明替换框架和引入重型游戏引擎。

主要游戏接口：

| 接口 | 作用 |
| --- | --- |
| `GET /api/game` | 读取伙伴、照料、物品、图鉴、旅行、纪念品、对手与记录 |
| `POST /api/game/greet` | 每日问候 |
| `POST /api/game/item` | 使用道具 |
| `POST /api/game/encounter` | 消耗寻缘符并返回相遇结果 |
| `POST /api/game/switch` | 切换同行伙伴 |
| `POST /api/game/journey` | 消耗行囊出发旅行 |
| `POST /api/game/battle` | 异步切磋并返回结果 |
| `GET /api/progress`、`POST /api/progress` | 学习进度读取与同步，奖励与同步结果关联 |

不能以现有接口支撑的内容，如实时联机、技能回合战斗、聊天、好友邀请、付费抽卡、装备、交易、排行榜、成就系统、地图关卡解锁和家园装修，应列为单独新增提案。现有对手列表的排序不等于正式排行榜。

当前学习记录由客户端提交，没有正式竞技所需的防作弊能力。不要设计带实际利益奖励的竞技承诺。

## 11. 希望 AI 交付的内容

按以下顺序输出，不能只给通用设计建议：

1. **整体概念**：一句话定位、世界观、美术方向、为什么适合键盘学习，以及与现有界面的变化。
2. **信息架构**：完整页面和模块关系、桌面与手机导航、每个主要入口的去向与返回方式。
3. **用户流程**：首次进入、每日回访、练习结算、照料、寻缘、旅行和切磋，写出触发条件、加载、成功与失败路径。
4. **关键高保真设计**：至少包含游戏主界面、词典选择、练习、学习结算、伙伴照料、图鉴寻缘、旅行和切磋，以及手机关键界面。每个页面标注主操作、层级和交互。
5. **组件与状态规范**：共用 HUD、面板、按钮、资源图标、任务进度、道具卡、伙伴卡、弹层、提示和错误状态。
6. **美术清单**：五只伙伴、阶段差异、场景、道具、纪念品、五行标识、Logo 与 ICO；标注静态图或动画、尺寸、透明背景、图层与移动裁切要求。
7. **动效规范**：给出触发与反馈时序、可跳过规则、减弱动效方案，不用装饰动效掩盖请求等待。
8. **落地分期**：先完成现有功能的完整视觉与交互闭环，再列出新增玩法。每个新增内容说明所需接口、数据与资源。
9. **待确认问题**：只列真正影响方案的选择，例如最终美术风格、登录替代方案、是否允许改变游戏规则。

如果交付可运行原型，应使用明确标识的演示数据，不接入真实密钥。原型内展示的新增能力必须在交付说明中标为原型演示，不宣称已接通生产后端。

## 12. 验收问题

- 首屏是否像一个有伙伴和目标的游戏世界，同时能迅速开始学习？
- 能否从首页完整走到练习、结算、真实奖励与伙伴互动，再回到学习？
- 连续完成两组学习时，是否正确区分成绩与每日唯一奖励？
- 未登录、登录不可用或断网时，是否仍能继续本地学习？
- 旅行中的限制、道具消耗、寻缘失败和切磋失败是否清楚？
- 界面是否忠实呈现现有异步切磋，而不是虚构实时玩法？
- 所有重要操作是否支持键盘、手机和减少动态效果场景？
- 是否保留旧进度、词典、备份与数据恢复能力？
- 每个新增机制是否明确标注开发成本，而不是隐含在设计稿中？
